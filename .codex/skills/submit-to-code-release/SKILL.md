# 创建新的发布批次

将需求任务中已完成、已验证的提交交给本批次专属的新发布任务。不复用历史“代码发布”对话，不扫描任务列表定位它。用户明确说“发布”即授权创建该批次任务，并在校验通过后推送与部署。

## 1. 确认交付边界

- 确认当前需求已完成并有独立提交；未完成时先继续实现，不能把半成品交给发布任务。
- 读取 `docs/project-memory.md` 及当前需求对应模块文档，遵守其中的发布和检查规则。
- 检查 `git status --short` 与相关 diff，区分本任务改动、其他任务改动和重叠文件。
- 保留工作区全部已有改动；禁止为了整理发布范围而回退、覆盖或丢弃其他任务内容。
- 记录已经执行的检查、未执行的检查及风险，不补写不存在的验证结果。

## 2. 形成简短发布清单

交接信息必须包含：

- 来源任务的 ID、标题和项目目录。
- 用户可感知的改动范围，按功能结果描述。
- 主要涉及文件及与其他活动任务的重叠情况。
- 已通过的检查及其准确结果。
- 尚未检查的内容、风险和当前是否已有提交。
- 同一工作区内仍在运行的任务；重叠任务未完成时，明确要求发布任务等待或确认后再整合。

不复制需求讨论、完整日志或无关历史。发布任务应从提交和最终差异判断实际内容。

## 3. 创建本批次的新任务

1. 使用项目列表定位当前 Git 项目，不使用任务列表查找旧对话。
2. 创建标题为“发布 YYYY-MM-DD 需求简称”的新 Codex 任务，默认使用该项目的独立 Worktree。
3. 新任务的首条消息只包含发布清单和下方执行要求，不要让它回读需求任务或历史发布任务。
4. 如果创建新任务明确失败，可在当前任务内创建临时干净发布 Worktree 继续；不得回退到复用旧“代码发布”对话。
5. 如果任务创建结果不确定，不重复创建或开始第二条发布链路；向用户说明当前状态。

发送给发布任务的要求必须包括：

- 重新读取项目发布规范并检查当前工作区。
- 从最新 `origin/main` 创建干净的 `codex/release-*` 分支，只整合明确提交，不从主工作区全量暂存。
- 根据同批次改动风险执行相应测试；涉及服务端、数据库、结算或实时同步时运行完整测试。
- 形成发布提交，使用仓库本地 Git 凭据推送 `HEAD:main`，检查生产环境，并回报提交号、测试结果和生产验证结果。
- 不打开 GitHub 登录页或把凭据发到对话。如果 Git 明确报告凭据缺失，只尝试一次后停在可继续的本地提交。

## 4. 跟踪与回报

- 创建成功只能回报“已创建发布批次”，不能回报“已发布”。
- 使用单目标任务等待机制跟踪新发布任务，不反复读取完整任务历史。
- 只有发布任务明确完成后，才向用户报告发布提交号、测试状态和生产结果。
- 发布完成后归档该批次任务，不将其变成新的长期发布对话。
- 发布任务请求批准或用户输入时，将请求留给用户处理，不代替用户扩大权限。
