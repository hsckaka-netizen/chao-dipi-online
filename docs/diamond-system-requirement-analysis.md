# 钻石系统需求逻辑底稿

## I. 核心要点快照

### 一句话定义

有效真人牌局结束后，每名玩家获得基础钻石；正向表现称号提供额外钻石，奖励与牌局历史在同一事务中幂等入账。

### 核心逻辑结论

- 当前规则版本为 `2026-08-24-v3`；钻石进入新计价单位，规则变化必须产生新版本，不能重算已结束牌局。
- 当前已开放钻石赚取、余额、流水、钻石商城消费、英雄抽卡/家园生产和管理员发放；仍不开放充值或玩家之间交易、赠送。
- 英雄抽卡付费单抽 300 钻石，十连原价 3,000 钻石、9 折实付 2,700；免费单抽每天北京时间 06:00 恢复 1 次且不累计。
- 每局基础 100 钻石，获胜不再额外增加钻石；正向称号按固定表加成，称号部分每局最多 50 钻石。
- 新计价单位上线时不改写历史牌局和历史奖励；向现有钱包发放等于切换前余额 9 倍的一次性“计价转换”补偿，使可用余额达到原余额 10 倍，并写独立流水。
- 负面或可能被刻意刷取的称号不奖励钻石。
- 钻石奖励不设每日获奖局数上限；每一局符合资格的牌局都按当前规则正常发放。旧版本下因每日上限未发放的历史奖励不追补。
- 每日对局任务在北京时间 06:00 刷新；任务钻石在玩家领取时独立入账，不计入单局基础与称号奖励公式，任务定义和奖励数值由 `daily-tasks.js` 集中配置。

### P0 必须实现

1. 账号级钻石钱包和不可变流水。
2. 牌局奖励公式和规则版本快照。
3. 与牌局历史同事务写入、按牌局和账号幂等。
4. 结算页展示基础、称号、实发数量与发放状态。
5. 登录玩家可看到当前钻石余额。

### 重大风险与约束

- 含机器人、游客、未登录玩家或重复账号席位的牌局不发钻石。
- 浏览器只展示奖励，不能决定数量或修改余额。
- 称号奖励只能读取已冻结的原始结算，不反向改变积分、胜负或称号。
- 规则变更必须产生新版本，已结束牌局不能按新数值重算。
- 数据库失败不能阻塞牌局结束；奖励进入重试，成功前显示“处理中”。

## II. 需求场景锚点

### 用户故事

| 角色 | 用户故事 | 成功标准 |
|---|---|---|
| 玩家 | 作为完成真人牌局的玩家，我希望获得基础钻石 | 无论输赢都有基础收益 |
| 表现优秀玩家 | 作为获得正向称号的玩家，我希望表现转化为额外奖励 | 展示每个奖励称号及数量 |
| 玩家 | 作为玩家，我希望看到准确余额 | 余额与服务端钱包、流水一致 |
| 管理员 | 作为管理员，我希望给指定玩家发放钻石 | 正整数钻石立即到账，重复请求不重复入账，并记录管理员与备注 |
| 运营维护者 | 作为维护者，我希望调整未来奖励而不改写历史 | 每笔奖励保存规则版本和明细 |

### 核心用例

| 用例 | 正常路径 | 异常闭环 |
|---|---|---|
| 真人局发奖 | 冻结结算 → 计算奖励 → 写历史 → 更新钱包 → 写奖励与流水 → 提交 | 任一步失败整体回滚并重试 |
| 重复结算 | 再次提交同一牌局 | 命中奖励主键和流水幂等键，不重复入账 |
| 无效牌局 | 含机器人或未登录席位 | 结算显示不符合奖励条件，不创建钱包流水 |
| 查询余额 | 登录账号请求钱包 | 返回余额、累计获得和最近奖励 |

## III. 业务模型定义

### 实体定义

| 实体 | 关键属性 | 说明 |
|---|---|---|
| 钻石钱包 | 账号、余额、累计获得、更新时间 | 服务端锁行更新，余额不得为负 |
| 牌局钻石奖励 | 牌局、账号、奖励日期、规则版本、计算值、实发值、状态、明细 | 同一牌局同一账号只有一条 |
| 钻石流水 | 账号、变动量、变动后余额、原因、关联牌局或商城购买、幂等键 | 不可变审计记录 |
| 奖励规则 | 版本、基础值、胜利值、称号表、称号封顶 | 当前没有数据库配置表或后台配置页，参数由 `diamond-rewards.js` 随代码发布 |

### 状态迁移

| 对象 | 原状态 | 触发 | 新状态 |
|---|---|---|---|
| 奖励 | 未计算 | 有效牌局结算冻结 | 处理中 |
| 奖励 | 处理中 | 事务成功 | 已发放 |
| 奖励 | 处理中 | 数据库事务失败 | 保持处理中并重试 |
| 钱包 | 当前余额 | 奖励已发放 | 余额增加并写流水 |

## V. 核心逻辑规则矩阵

### 奖励公式

`实发钻石 = 基础奖励 + min(称号奖励合计, 50) + 英雄技能奖励`

| 奖励项 | 条件 | 钻石 |
|---|---|---:|
| 基础奖励 | 有效真人牌局 | 100 |
| 胜利奖励 | 无论输赢均不额外增加 | 0 |
| MVP | 获得 `mvp` | 30 |
| 辅 | 获得 `support` | 20 |
| 精 | 获得 `precision` | 10 |
| 神 | 获得 `god` | 20 |
| 天之上 | 获得 `heaven` | 额外 10 |
| 尽 | 获得 `exhausted` | 10 |
| 擎 | 获得 `pillar` | 额外 10 |

英雄技能奖励读取正式发牌时锁定的英雄快照与原始结算事实，独立于称号奖励 50 钻封顶；六英雄的条件和星级数值见 `docs/card-system-requirement-analysis.md`。

`couch`、`pit`、`stiff`、`stiffest`、`thunder`、`god-pit` 不提供称号钻石。相同称号去重后再计算。`神 + 天之上` 和 `尽 + 擎` 的高级称号采用增量奖励。

### 有效牌局

- 所有席位均为已登录真人账号。
- 同一账号在同一局只能占一个席位。
- 牌局自然完成并生成唯一 `game_id`。
- 每日实发奖励局数不限；不再根据 `reward_date` 查询当日获奖局数或转为零实发。

### 幂等与一致性

- 奖励唯一键：`(game_id, account_id)`。
- 流水幂等键：`game_reward:{game_id}:{account_id}`。
- 牌局历史、玩家结果、称号、奖励、钱包和流水在同一数据库事务提交。
- 钱包更新前锁定账号钱包行，避免并发结算导致余额或流水错误。
- 管理员发放只允许增加 1～1000000 的整数钻石；不改变任何牌局奖励记录。
- 管理员发放使用独立请求编号，余额与 `admin_grant` 流水在同一事务写入；流水明细保留管理员账号和备注。

## VI. 交互与异常协议

### 信息展示

- 顶部账号区域展示 `💎 当前余额`。
- 结算页每名玩家展示钻石实发值。
- 当前玩家可看到自己的拆分：基础、奖励称号、称号封顶和发放状态。
- 状态文案限定为：处理中、已发放、不符合奖励条件、发放失败。
- 本人结算拆分同时展示英雄技能条件、次数、星级封顶和英雄追加钻石；其他玩家不显示余额。
- 含机器人牌局在开局和结算处明确说明不发钻石。

### 异常闭环

- 数据库暂不可用：牌局正常结束，奖励显示处理中并由服务端重试。
- 重复请求或服务重启重放：返回既有奖励，不重复增加余额。
- 跨北京时间零点重试：奖励日期按牌局完成时间计算，不按重试时间漂移。
- 规则升级：新牌局使用新版本；历史奖励使用保存的旧版本与明细展示。

## VII. 研发与测试参考

### API

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/diamonds/me` | 返回当前账号余额、累计获得和最近奖励 |
| `POST` | `/api/admin/diamonds/grants` | 管理员向指定玩家发放钻石 |
| `POST` | `/api/heroes/daily-tasks/claim` | 领取已完成的每日对局任务钻石与建材 |

### 关键测试

- 无称号玩家无论输赢固定获得 100。
- 获得 MVP 的玩家获得 130。
- 多个正向称号累加后称号部分不超过 50。
- 英雄技能奖励在称号封顶之外追加，并与基础/称号奖励同事务入账。
- 免费单抽不扣钻石，重放相同请求不重复发放角色或改变北京时间 06:00 的恢复窗口。
- 负面称号不会产生奖励。
- `神 + 天之上` 和 `尽 + 擎` 按增量值叠加。
- 含机器人或未登录席位的牌局不发奖。
- 同一牌局重复保存不重复加余额或写流水。
- 同账号并发结算时，每局都正常发放且钱包余额、流水与奖励记录一致。
- 同一账号同一天完成超过 10 局有效牌局时，第 11 局及后续牌局仍正常发放。
- 数据库回滚后钱包、奖励和流水均无半成品。
- 结算页从处理中切换到最终实发状态。
- 同一账号、刷新日期和任务编号只能领取一次每日任务奖励；重复请求返回既有结果，不重复增加钻石或建材。
