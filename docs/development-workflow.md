# 开发、验收与发布流程

## 需求任务

- 每项可独立验收、提交和回滚的需求使用一个新任务。
- 在 Codex 中优先从本 Git 项目创建独立 Worktree。
- 新 Worktree 根据 `.codex/environments/environment.toml` 自动执行 `npm ci`。
- 开始时只读 `AGENTS.md`、`docs/project-memory.md` 和本需求对应的模块文档。
- 先搜索定位，再读取相关代码片段；不默认读取全部大文件、历史任务或无关设计稿。
- 保持需求范围，保留其他任务和用户已有改动，不做无关重构。
- 需求任务不得直接推送 `main` 或部署。

Codex 顶部快捷操作已配置为：启动本地服务、语法检查、完整测试。

## 分级验收

| 改动类型 | 最低检查 |
| --- | --- |
| 纯文案、无布局影响的小改动 | 语法检查和直接相关测试 |
| 桌面或移动端布局、交互、输入操作 | 语法检查、相关测试、实际打开受影响页面 |
| 响应式布局 | 至少检查一个桌面尺寸和一个目标移动端尺寸，并确认无越界或横向滚动 |
| 牌局规则或普通服务端逻辑 | 直接相关测试 |
| 结算、数据库、实时同步、认证、跨模块改动 | `npm run check` 和完整 `npm test` |
| 素材或前端资源 | 检查内容版本、目标尺寸和受影响页面 |

- 不为无关功能扩大验收范围。
- 仅调整已有配置项的数值、且不改变计算结构、数据库或接口时，按用户约定不运行自动化测试，只核对目标配置与对应文档；超出纯数值配置范围时仍按上表验收。
- 页面检查只覆盖受影响状态和尺寸，不默认制作截图报告。
- 如果测试因沙箱端口或权限失败，应区分环境失败与断言失败，再按允许的方式复核。

## 需求交接

需求完成并准备进入发布批次时，形成独立提交，并只交付一份简短发布清单：

1. 需求名称和结果。
2. 提交号或分支。
3. 修改文件或模块。
4. 已完成的检查。
5. 依赖关系、数据库或配置变化。
6. 已知风险和回滚注意事项。

不复制整段需求讨论、工具日志或完整开发过程。发布任务以提交和最终差异为准，不回读需求对话。

不需要为正常完成的任务创建 `handoff.md`。只有任务中断、存在未完成改动、需要保留本地服务或复杂状态时，才创建不超过 30 行的临时交接文件。

## 发布批次

- 用户明确说“发布”、“发布吧”或“统一发布”时，表示授权创建一个新的批次发布任务，并在校验通过后推送 `main` 和触发 Render；不再追加询问“是否创建发布任务”。
- 每批新建一个短任务，命名为“发布 YYYY-MM-DD 需求简称”。不复用、搜索或唤醒历史“代码发布”对话。
- 新发布任务使用同一本地项目和新 Worktree，从最新 `origin/main` 创建 `codex/release-*` 分支，只按交接清单的明确顺序整合指定提交。
- 发布前确认来源提交、依赖顺序、工作区状态和最终差异；不从主工作区全量暂存。
- 根据批次最高风险执行对应检查。无冲突的小型 UI/文案批次不重复完整测试；结算、数据库、实时同步、认证或跨核心模块改动在最终整合态运行完整测试。
- 整合和检查通过后推送 `HEAD:main`；推送后由发布脚本等待部署，避免对话反复手工轮询。
- 确认生产首页、资源版本和本次涉及的必要健康接口，回报最终提交、测试和生产证据，然后归档该发布任务。
- 需求任务只用单目标等待机制跟踪新发布任务，不频繁读取它的完整历史。如果新任务创建结果不确定，不立即重复创建，先避免产生重复发布。
- 只有在用户已明确要求发布且新发布任务创建明确失败时，当前需求任务才可在临时干净发布 Worktree 中继续同一流程；不回退到复用旧发布对话。

### GitHub 认证与操作授权

- GitHub 凭据属于本地主机的 Git 凭据存储，不属于某条 Codex 对话。新发布任务在同一主机上继续使用仓库 `origin` 和 macOS Keychain，不为了“保留登录”复用长对话。
- 优先使用本地 Git 推送，不默认打开 GitHub 网页、安装连接器或重新执行登录。
- Codex 对执行外部写入的安全确认与 GitHub 身份认证是两件事。前者可能在推送前显示一次系统确认；不应将它说成“重新授权 GitHub”。
- 如果 Git 明确报告凭据无效或缺失，推送只尝试一次，随后停在本地发布提交，保留可继续状态并说明需要在本机恢复凭据。Token、密码或密钥不得发到对话、日志或提交中。

### 本地发布脚本

- 可用 `npm run release -- --message "提交说明" --level ui` 执行常规前端/素材发布：脚本会列出当前改动、运行差异检查、语法检查和资源版本测试，确认后提交、推送 `main` 并轮询生产首页与健康接口。
- 涉及服务端、数据库、结算、实时同步、认证或跨模块改动时，使用 `npm run release -- --message "提交说明" --level full`，额外运行完整测试。
- 脚本可从 `main` 或干净的 `codex/release-*` 分支执行；从发布分支执行时推送 `HEAD:main`，避免为了占用本地 `main` 而复用某个旧 Worktree。
- 仅做生产资源状态确认时，使用 `npm run release -- --verify-only`，不会提交、推送或写入生产；若由自己稍后验收，追加 `--no-verify` 可在推送后直接结束。
- 脚本会暂存当前工作区的全部改动；运行前必须确认脏工作区只包含本批次范围，混有其他任务改动时不要使用脚本直接发布。

## 低 Token 工作方式

- 需求明确时直接实现，不重复复述需求或输出长计划。
- 搜索、读取和检查尽量批量执行，并限制日志长度。
- 获得足够证据后停止扩展调查；不为了“更保险”读取无关文档或旧任务。
- 长期规则写入对应模块文档；临时讨论、日志和失败尝试不写入长期上下文。
- 最终回复只保留完成内容、检查结果、提交号和必要风险。
